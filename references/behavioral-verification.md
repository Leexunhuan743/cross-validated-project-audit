# 真实用户路径与运行时验证

只在 Hypothesis/Finding 涉及用户可见行为、公共 API/CLI、迁移、平台语义、并发交错或第三方运行时时读取本文件。目标是验证真实入口，而不是为积累通过结果而运行更多测试。

## 1. 选择公共入口

| 工件 | 优先入口 | 关键观察 |
|---|---|---|
| CLI | 实际命令、参数组合和批量调用 | 退出码、stdout/stderr、错误文本、状态变化 |
| API/服务 | 公共 endpoint、SDK 或协议请求 | 鉴权上下文、响应、错误、重试、副作用 |
| UI | 用户可见页面和控件 | gating、导航、取消/重入、持久状态、键盘/a11y |
| 数据/迁移 | 真实旧数据形状和迁移入口 | 兼容读取、部分失败、恢复、重试、回滚 |
| 库/SDK | 公开 export 和典型调用方 | 签名、默认值、异常、版本与安装产物 |
| 并发/生命周期 | 生产调度、取消、关停和资源边界 | 交错、超时、释放、重复调用、背压 |

优先使用用户或调用方真正能触达的入口。测试 helper、内部函数和 mock 只能支持局部主张，不能替代公共路径。

## 2. 记录验证档案

对每个需要运行时 Evidence 的 Hypothesis/Finding 保留：

```text
入口：<命令、endpoint、UI 路径、公共函数或迁移入口>
环境：<OS、版本、构建模式、依赖版本>
前置状态：<数据、配置、身份、文件系统状态>
操作/命令：<可重复步骤；敏感值用占位符>
预期：<来自需求、契约或既有兼容行为>
实际：<可观察输出、状态或副作用>
重复性：<repeatable / conditional / single-observation；与 Evidence Reproducibility 保持一致>
清理：<已删除的临时资源和未触碰的真实系统>
```

复现细节只保留证明问题所需的最小信息，不回显秘密、真实用户数据、私钥、令牌或敏感 URL。

## 3. 安全执行顺序

1. 静态追踪入口、调用链、保护条件和可能影响。
2. 复用仓库已有、已检查且与目标 Hypothesis/Finding 直接相关的测试或工具。
3. 调用最小公共路径，并限制输入、时间、资源和网络范围。
4. 需要修改状态时使用仓库外隔离副本、临时 worktree、临时数据库或可丢弃环境。
5. 需要安装工具、下载依赖、扩大网络、使用凭据、付费资源、外部写入或生产访问时暂停并请求授权。
6. 无法获得目标平台时，查阅对应版本的官方契约。契约明确覆盖完整调用链、版本、配置和触发条件时，可形成强的纯契约 Evidence；若主张仍依赖目标状态或集成语义，则记录目标环境验证缺口，由主代理在 Decision/gate 层处理。
7. 无法本地复现时，仅在取得所需的用户授权并经主代理批准后，才可在真实环境加统一前缀的临时埋点，由现场人员复现并回传取证日志；定位后移除埋点、保留防御性逻辑；埋点与日志按脱敏纪律处理。
8. 清理探针、临时埋点、临时文件、进程、容器和测试数据，再复核原工作区及真实环境状态。

不要为了前向验证直接执行未检查的 lifecycle、build、install、hook 或测试脚本。先读取脚本和配置，识别下载、任意代码执行、秘密访问和外部副作用。

## 4. 按风险构造最小场景

- **正常路径**：先确认最基本的用户工作流能完成，核对输出与需求，而不只检查进程是否退出或页面是否渲染。
- **常见变化**：覆盖用户自然会尝试的空值、边界值、重复调用、不同顺序或批量输入；不生成需要多个罕见前提的理论场景，除非影响是 Critical 且前提真实存在。
- **错误与取消**：覆盖缺失输入、明显非法输入、依赖失败、取消、超时和部分完成；检查原始错误是否保留、资源是否释放、状态是否可安全重试。
- **旧数据与旧调用方**：使用代表性旧 schema、配置、序列化值或调用签名；验证兼容读取、迁移、fallback 和明确的不兼容门禁。
- **并发与生命周期**：构造最小交错，明确同步点、预期不变量和超时上限；无法稳定复现时记录交错假设和环境限制，不把偶发信号当确认事实。

## 5. Evidence Strength、可复现性与 Decision

本节**只产出/评价 Evidence，不直接作 Decision**；每条运行时 Evidence 使用任务已载入的统一 Strength / Reproducibility 词汇标注。最终 Decision、Severity 与 Confidence 由主代理在 Finding/Decision 层裁决。

- 真实公共路径有可重复步骤并稳定复现目标行为：通常至少 `ES3`；只有在与该主张相关的目标平台/版本/构建条件下通过真实公共入口复现，才达到 `ES4`。对应版本权威契约可提高整体 Confidence，但不能把非目标环境或仅内部 helper 的复现升级为 `ES4`。
- 完整静态调用/数据/契约链可自行重查但缺执行复现：通常 `ES2`；局部代码/日志/输出 indication 且条件未闭合：`ES1`。这些等级描述 Evidence 质量，不直接等于 Confidence。
- 保护条件、安全反例、不可达约束或真实运行结果否定主张：形成 DIRECT refuting Evidence。
- 行为事实已证实、但是否接受属于产品/兼容策略：Evidence 只记录事实与影响，是否需要用户/产品决策由主代理决定。
- Evidence 冲突时，优先比较 Strength、Reproducibility、目标版本/公共路径相关性和是否存在未解释前提；目标环境可重复反证通常高于本地模拟或局部静态 indication。保留双方 Evidence 并调查冲突原因，不按数量投票。

代理报告本身、无来源日志片段、测试通过或一次偶发失败都不能单独作为决定性 Evidence。

## 6. 与异质验证方法配合

- 运行时/公共行为风险优先把 `user-path-trace` 与另一种不同 archetype 配对，例如 `implementation-trace`、`state-invariant-analysis` 或 `contract-spec-verification`。
- 不向第二条发现路径泄露第一条路径的预期结论；同一公共路径被两个代理照抄执行，不自动形成方法异质性。若要声称 independent validation，除本条的执行隔离外还须满足 [audit-ledger.md](audit-ledger.md) §3.4 的完整判据（权威）。
- 主代理按当前 risk coverage 检查风险主张是否由不同 archetype 与不同证据源覆盖；相同代码推断不能冒充异质验证，也不能单凭执行次数声称 independent validation。
- 需要写探针或测试时，由主代理批准隔离位置和清理方式；调查阶段子代理不得修改项目源码，也不得直接写最终 state root。自己的 investigation JSON 只能通过平台消息或主代理批准的 state-root 外 staging 交付，再由主代理按接收事务写入 canonical 路径。

## 7. 无法验证时的报告

说明：已完成的静态追踪和支持 Evidence；缺失的目标环境、版本、凭据或外部条件；能区分真假的最小后续验证；该缺口是否影响门禁交由主代理在统一 reporting/gate 层判断，本模块不自行映射 gate。

不得用"看起来应该""两个代理都认为"或其他平台模拟替代缺失证据。
