# 报告契约与完成门槛

在输出最终审计结果前读取本文件。报告按候选问题聚合，不按代理逐份倾倒。

## 报告顺序

1. **门禁结论**：`READY`、`READY-WITH-CONDITIONS`、`BLOCKED` 或 `INCOMPLETE`，附一句证据化理由。
2. **范围与基线**：工件、不可变 refs、审计模式、要求、假设、排除项。
3. **已确认问题**：按严重度排序。每项包含位置、归因、直接证据、原因→影响、触发条件、主代理复核方式、建议修复和通过条件。
4. **决策项与条件项**：分别列出 `NEEDS-DECISION` 和 `CONDITIONAL`，不要混入已确认缺陷。
5. **重大反驳项**：列出会改变结论但已 `REJECTED` 的候选及主代理反证。
6. **已验证正确**：只列高风险且有证据的行为，不输出冗长“检查过一切”清单。
7. **检查与环境**：实际运行的关键检查、基线失败、未运行原因和平台/版本。
8. **覆盖与残留缺口**：覆盖矩阵、未验证平台、未覆盖交互、容量或代理降级。
9. **追溯附录**：候选问题账本与代理覆盖矩阵；可压缩重复来源，但保留来源代理和主代理裁决。

## 阻断与解除条件

门禁状态按以下顺序裁决：

| 条件 | 门禁结论 |
|---|---|
| 存在已确认、现实可达且与发布相关的 Critical/High | `BLOCKED` |
| 关键证据、环境或独立覆盖缺失，无法可靠判断是否存在阻断项 | `INCOMPLETE` |
| 没有已确认阻断项，但发布前仍有明确、可验证的非阻断前置条件 | `READY-WITH-CONDITIONS` |
| 完成门槛满足，且没有阻断项或未完成条件 | `READY` |

`CONDITIONAL`、`NEEDS-DECISION` 是候选问题裁决，不直接等于门禁状态。根据其是否造成关键判断缺口，映射到 `INCOMPLETE` 或 `READY-WITH-CONDITIONS`；不得用它们覆盖已确认的阻断缺陷。

每个 `BLOCKED` 项必须有可执行的解除清单：

```text
[ ] <需要完成的动作>
    退出条件：<可观察、可测试、可判定的通过条件>
```

若影响仍属推断，不要阻断；裁决为 `CONDITIONAL` 或 `NEEDS-DECISION`，再按上表判断门禁。若缺陷已确认但尚无具体修复方案，仍可阻断，解除动作写为“确定、实施并验证修复方案”，退出条件写为“原触发路径不再失败且相称回归通过”。报告文字本身不是通过门禁，检查与退出条件才是。

## 无确认问题的措辞

独立覆盖和关键检查达标时：

> 在已审计范围和已执行检查内未发现已确认缺陷。

未完成独立交叉验证时：

> 已完成的单代理/部分审查未发现候选问题，但未完成独立交叉验证，不能视为全面无缺陷结论。

绝不声称“绝对安全”“没有 bug”或“所有场景均正确”。

## 完成清单

- [ ] 每个有实际影响的候选项都有严重度、归因、主代理复核记录和最终裁决。
- [ ] 所有 Critical/High 已获得两个独立视角，或明确记录无法交叉验证的缺口。
- [ ] 报告包含范围、确认问题、条件/决策项、重大反驳、正确行为、检查、覆盖和残留风险。
- [ ] 每个阻断项都有解除动作和可判定退出条件；无证据的推断没有被升级为阻断。
- [ ] 临时证据包、探针和隔离工作区已清理；审计模式没有修改项目，修复模式只保留预期改动。
- [ ] 若实施修复，每个批次都完成 finding→fix 映射、新代理复核、主代理裁决和相称回归。
