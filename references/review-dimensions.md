# 审查维度与代理分工

在设计多代理覆盖矩阵时读取本文件。只选择与工件相关的维度，并为每个代理设置一个主要职责和一个高风险重叠目标。

## 实现类工件

| 维度 | 重点检查 | 典型适用场景 |
|---|---|---|
| 正确性与不变量 | 输入到输出的数据流、状态转换、边界值、错误路径、旧行为差异 | 所有代码变更 |
| 安全与隐私 | 信任边界、鉴权授权、注入、凭据、日志、隐私数据、依赖风险 | 外部输入、身份、网络、文件、序列化 |
| 数据与迁移 | schema、事务、幂等、兼容旧数据、回滚、部分失败、一致性 | 数据库、缓存、文件格式、迁移 |
| 并发与生命周期 | 竞态、锁顺序、取消、超时、资源释放、启动关停、重试 | 多线程、异步、队列、长连接 |
| 接口与兼容性 | API、CLI、UI 状态、错误契约、版本兼容、i18n、可访问性 | 公共接口和用户交互 |
| 测试与回归 | 测试判别力、遗漏分支、错误断言、脆弱 mock、旧缺陷复现 | 所有非平凡变更 |
| 性能与资源 | 复杂度、内存、I/O、批处理、缓存、限流、背压 | 热路径、大数据、服务端任务 |
| 构建与交付 | 配置、feature flag、依赖、生成物、打包、升级、回滚、文档主张 | 发布、CI、部署、依赖升级 |
| 可观测性与恢复 | 错误传播、日志脱敏、指标、告警、重试安全、灾难恢复 | 后台任务、分布式系统、关键流程 |

## 计划类工件

| 维度 | 重点检查 |
|---|---|
| 事实与可行性 | 关键假设是否与现有代码、接口、约束和资源一致 |
| 完整性与顺序 | 依赖、迁移顺序、兼容阶段、所有受影响消费者是否覆盖 |
| 失败模式 | 部分完成、并发发布、旧版本共存、回滚和恢复路径 |
| 验收与测试 | 每项成果是否可观察、可测试，测试能否区分成功与失败 |
| 安全与运维 | 权限、秘密、监控、容量、部署窗口和责任边界 |

## 组合示例

- 小型后端修复：正确性代理 + 测试/对抗性代理；两者都检查核心不变量。
- 鉴权变更：安全代理 + 会话/状态代理 + 回归代理；安全边界由前两者独立重叠。
- 数据迁移：数据完整性代理 + 回滚/运维代理 + 调用方兼容代理；旧数据路径至少双重覆盖。
- CLI 或 UI 功能：契约/交互代理 + 状态正确性代理 + 测试代理；错误和取消路径交叉覆盖。
- 实施计划：架构可行性代理 + 失败/回滚代理 + 验收/测试代理；关键外部依赖由至少两者验证。

## 保持独立性

- 在发现阶段给各代理相同的已确认事实，但不要共享其他代理的候选问题。
- 不要让所有代理都执行“全面审查”；明确划分主责才能获得真正不同的视角。
- 对同一高风险不变量使用不同检查方法，例如静态调用链、测试反例、状态机分析或契约对照。
- 第二阶段挑战者可以看到待验证主张，但必须使用中性措辞，并被要求主动寻找反证。
- 同一模型的多次回答可能相关。只把可复现证据、独立代码路径或权威契约视为实质交叉验证。

## 降噪规则

- 只报告能说明触发条件和实际影响的问题。
- 不把个人风格、无影响的重命名或缺少可选注释列为缺陷。
- 不因“理论上可能”提高严重度；同时评估可达性、保护条件和失败后果。
- 不因测试通过就认定实现正确；检查测试是否覆盖生产函数并能在缺陷存在时失败。
- 不因多个代理重复同一主张就认定正确；主代理仍需回到原始证据。
