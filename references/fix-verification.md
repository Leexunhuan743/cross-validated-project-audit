# 修复与 fix-commit 验证

当用户要求实施修复，或审计对象是整改 commit/分支时读取本文件。目标不是证明“改过了”，而是证明原问题消失、测试能识别回退且没有引入更高价值的新缺陷。

## 1. 建立修复映射

为每个原 finding 建立：

`Finding ID | 根因 | 修复文件/符号 | 行为变化 | 验收测试 | 回退时应失败 | 残留风险`

读取 PRE-fix 代码和原始报告。不要仅根据 commit message 或修复摘要判断意图；核对实际 diff、调用者和测试。

## 2. 批前门槛

- 记录构建、静态检查和相关测试基线；既有失败单独列出。
- 把 3–5 个相互关联的修复组成一批；高风险或不可逆修复可以单独成批。
- 创建批次 todo，声明允许修改的路径和验收条件。
- 保护用户已有改动；不把无关格式化、重构或文档更新混入修复批次。

## 3. 实施与主代理验证

1. 实施最小必要修复。
2. 运行定向检查，再运行成本相称的回归检查。
3. 对关键测试做判别力验证：优先在 PRE-fix 版本运行；若需恢复旧 guard/路径或做变异测试，只能在仓库外副本、临时 worktree 或其他可丢弃隔离环境中进行。只读审计不得修改用户原工作区；仅当用户明确要求修复时，才能在授权路径内保留项目编辑。
4. 对运行时、平台、并发和第三方语义调用真实生产函数；无法实证时保留 `CONDITIONAL`。

## 4. 新代理批次复核

为每个受影响子系统使用未参与实现的新只读代理，并提供：批次 finding→fix 映射、精确 diff、验收标准、基线失败及允许检查。

要求复核者分别回答：

- 原 finding 是否真正消失，证据是什么？
- 新测试是否会在 PRE-fix 行为下失败？
- 是否破坏旧数据、旧调用方、错误/取消路径或恢复能力？
- 被替换的旧 helper、writer、route、export 或 feature flag 是否仍可达？
- 修复是否引入新的 Critical/High/Medium？

## 5. 裁决反馈

- `CONFIRMED-FLAW`：立即修复并重跑受影响检查。
- `REJECTED-CLAIM`：记录主代理反证，不为满足代理意见而修改正确代码。
- `NEW-REGRESSION`：按严重度处理；新的 Critical/High 在进入下一批前解决。
- `CONDITIONAL`：写清缺失环境、平台或契约，不冒充已验证。

每批更新候选问题账本和修复映射，主代理确认门槛通过后才进入下一批。

## 6. 收尾轮

1. 处理成本低且明确的剩余 Medium/Low；需要产品决策的保留为 `NEEDS-DECISION`。
2. 只有项目策略、计划或用户要求时才更新 CHANGELOG、生成物或发布说明。
3. 检查 Git 交付完整性：遗漏/杂散文件、exports、lockfile、vendor、markers、生成物和 ignore 规则。
4. 清理临时证据包、探针、隔离 worktree 和构建残留；确认工作区只包含预期修改。
5. 运行最终回归，并报告未运行检查、既有失败和平台缺口。
